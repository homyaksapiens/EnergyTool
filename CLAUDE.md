# EnergyTool AI-консультант — хакатон МТС True Tech Hack&Change 2026

ИИ-консультант для сайта МТС EnergyTool: понимает задачу клиента, задаёт уточняющие вопросы, подбирает продукт
EnergyTool по базе знаний, объясняет простым языком и передаёт менеджеру заявку с резюме диалога.

## Источники правды
- `Тз (1).pdf` — ТЗ кейса (задача, ЦА, ограничения, критерии оценки)
- `техчать.md` — технический регламент: формат сабмита, прокси, лимиты, формула оценки
- `данные/` — материалы организаторов. **Не коммитить и не публиковать** (запрет ТЗ):
  - `knowledge-base.zip` — база знаний (единственный допустимый источник фактов)
  - `demo_questions.csv` + `demo_output.csv` — 18 демо-вопросов с эталонными ответами (ориентир стиля и полноты)
  - `sample_submission.zip` — минимальный пример сабмита (рабочие вызовы `/embeddings`, `/rerank`, `/chat/completions`)
  - `requirements.txt` — **разрешённый набор пакетов** с версиями; в сабмите использовать только их
- ТЗ и регламент расходятся в одном: ТЗ разрешает класть готовый индекс в сабмит, регламент запрещает. Следуем регламенту

## Две части сдачи

### 1. Автосабмит → LLM-судья (50% онлайн-этапа; 0 баллов = недопуск к экспертизе)
- ZIP, файлы в корне: `solution.py` (точка входа), `requirements.txt`, при необходимости другие **корневые** `.py`.
  Вложенные папки не переносятся. Данные, индексы, конфиги, `.whl` не класть. `pip install` из кода запрещён
- Вход: `$DATA_DIR/questions.csv` (`id,question`) и `$DATA_DIR/knowledge-base.zip`; `DATA_DIR` по умолчанию `data`.
  Диалог приходит одной строкой в `question`: реплики `Пользователь: …` / `Ассистент: …` через перевод строки,
  отвечать на последнюю реплику пользователя. Между `id` состояние не переносится
- Выход: `submission.csv` в рабочем каталоге, UTF-8, ровно `id,answer`, ответ на каждый id, непустой, ≤ 10 000 символов.
  Пример организаторов пишет ответ в одну строку (`" ".join(answer.split())`) с `QUOTE_ALL`
- Прокси OpenAI-совместимый, адрес и ключ — `LLM_BASE_URL`/`OPENAI_BASE_URL`, `LLM_API_KEY`/`OPENAI_API_KEY`:
  - генерация — `POST /chat/completions`, модель **Qwen3.8-27B** из `LLM_MODEL`/`GEN_MODEL`/`OPENAI_MODEL` (не хардкодить)
  - эмбеддинги — `POST /embeddings`, `EMB_MODEL` (BAAI/bge-m3)
  - реранкер — `POST /rerank` `{model, query, documents, top_n}`, `RERANKER_MODEL` (Qwen3 Reranker 8B), необязателен
  - ещё доступны `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS`, `TOP_K`, `CHUNKER`, `RERANKER_TOP_N`.
    Чтение переменных — как в `env()` примера: значение, равное имени переменной, считается пустым
- Лимиты: **20 минут на весь прогон**, 8 CPU / 16 ГБ, ZIP ≤ 128 МБ, **5 сабмитов в день** (сброс 00:00 МСК).
  Индекс строить при запуске. На 429 / 5xx / таймаут — ограниченные повторы с паузой
- Tool calling и thinking-режим прокси не гарантированы: в `solution.py` не опираться на вызов инструментов,
  вырезать `<think>…</think>`, если модель его выдаёт. Версия Python платформы неизвестна — писать под 3.10+
- Оценка: судья сравнивает ответ с baseline (не раскрыт) относительно golden-ответа, два раунда со сменой порядка,
  балл за вопрос 0…1. `Score = 0.7·MatchRate + 0.3·WinRate`. Публичный лидерборд — public-часть вопросов, итог — private

### 2. Финальная сдача → экспертная оценка
- Веб-чат: многошаговый диалог; кнопка «Новый диалог» полностью сбрасывает контекст; **режим отладки**
  (время ответа + документы БЗ, которые использовал бот); сбор заявки — **ФИО, телефон, название компании** + резюме диалога
- История **всех** сессий (в том числе без заявки) сохраняется и доступна для проверки
- Репозиторий: README (назначение, архитектура, одна команда запуска через Docker, переменные, порты, зависимости,
  порядок проверки, ограничения), `Dockerfile`, `compose.yaml`, `.dockerignore`, зависимости с `==`, `.env.example` без ключей.
  Приватный репозиторий → открыть доступ аккаунту `hack-and-change-2026`
- PDF-презентация: на первом слайде — порядок проверки и ссылка на репозиторий (и на развёрнутый интерфейс, если есть)
- Веса экспертизы онлайн-этапа: работоспособность 30%, качество консультации 25%, скорость и стабильность 15%,
  архитектура 15%, безопасность/зависимости/документация 10%, презентация 5%

## Поведение консультанта
- Факты о продуктах, тарифах, ценах, характеристиках и условиях — **только из базы знаний**. Знания модели
  об энергетике не использовать. Ответа в БЗ нет → прямо сказать и предложить связаться со специалистом
- Тема — только продукты EnergyTool и связанные задачи клиента. Техдокументация и настройка приборов — вне компетенции
- Запрос неясен или найденного мало → уточняющий вопрос, а не ответ наугад
- Обычно ≤ 150 слов (на резюме заявки ограничение не распространяется)
- Стиль эталонов `demo_output.csv`: 40–80 слов, от лица компании («мы»), сначала прямой ответ («Да, …» / «Нет, …»),
  затем 1–2 предложения с фактом или оговоркой из БЗ, в конце **один** уточняющий вопрос о ситуации клиента.
  Если клиент не готов оставить телефон — не настаивать и продолжать консультировать (демо №18)
- Границы продуктов и когда нужен специалист — в `00-reference/02-product-scope-and-limits.md`. Например, МТС не продаёт
  электроэнергию; результат поиска потерь — список проверок, а не факт хищения; названия клиентов и производителей не раскрываются
- ЦА: малый и средний бизнес (выросли счета, ценовая категория, пиковые часы), энергетики предприятий (учёт, потери),
  правления СНТ, сетевые организации (хищения), региональные менеджеры МТС. Пишут своими словами, без терминов

## База знаний (`knowledge-base.zip`)
19 файлов `.md`, ~130 тыс. символов, ~150 разделов `##`/`###`. Таблицы — в формате pandoc (рамки из `-----`)
- `00-reference/` — карта продуктов, числовые показатели и оговорки, границы продуктов, что нужно для расчёта и заявки
- `10-energy/` — ликбез: рынок, ценовые категории, пороги мощности, учёт, рост счёта, микрогенерация, нормативка, FAQ
- `20-products/` — обзор портфеля (`20`) и шесть направлений: выход на оптовый рынок (`21-orem`),
  облачная платформа учёта (`22-askue`), солнечные станции — сетевые и гибридные с накопителями (`23-solar`),
  поиск коммерческих потерь (`24-losses`), распознавание показаний по фото (`25-meter-reading`), общие вопросы (`26-general`)

## Архитектура
Одно ядро для сабмита и веба: `Consultant.answer(messages) -> {text, sources, timings, reranked, fallback}` —
разбор диалога → гибридный поиск → один вызов LLM → чистка ответа. Tool calling не используется

`bot/` — ядро, **только плоские модули** (в ZIP идут как корневые), зависимости — только из `данные/requirements.txt`:
- `solution.py` — точка входа сабмита: пишет запасной `submission.csv` сразу, обновляет каждые 20 ответов,
  эмбеддинги базы и всех запросов считает пачками заранее, параллелит по `MAX_WORKERS`, бюджет времени `ET_TIME_BUDGET`
- `consultant.py` — разбор диалога (`Пользователь:`/`Ассистент:`), запросы к базе, реранк, вызов LLM, вырезание `<think>`
- `kb.py` — загрузка zip, разбор pandoc-таблиц в строки «Шапка: значение; …», чанки по `##`/`###` (~240 шт.),
  BM25 с грубым русским стеммингом + эмбеддинги, слияние списков через RRF
- `prompts.py` — системный промпт и запасной ответ; `llm_client.py` — httpx-клиент к прокси с повторами;
  `settings.py` — переменные окружения платформы и свои `ET_*`
- Если эмбеддер или реранкер недоступны — скрипт продолжает на BM25 (проверено на LM Studio)

Планируется: веб (раздел «Веб» ниже) и попарный LLM-судья в `eval/`

## Веб (зона Дениса Л. и Егора Б., решения от 10.11)
- **Стек:** бэкенд — FastAPI (Python) поверх ядра из `bot/`; фронтенд — чистые HTML, CSS и JavaScript без фреймворка
  и без сборки (пример стека от организаторов: Python, FastAPI, Docker, JS/TS). Владелец веба слабо знает фронтенд:
  код фронта простой, разбит по файлам, с комментариями на русском; React и сборщики не используем
- **API фронт ↔ бэк** — раздел 4 `CONTRACTS.md`; фронт можно делать на примерах ответов оттуда, не дожидаясь бэкенда
- **Экраны:**
  1. Страница-заглушка сайта Energytool: **кнопка чата в шапке**; кнопка «Оставить заявку» открывает тот же чат —
     чат вместо формы (в ТЗ клиент заполняет форму, а менеджер всё уточняет по звонку)
  2. Чат **открывается на весь экран**: приветствие, быстрые кнопки типовых задач, сообщения, индикатор ожидания,
     «Новый диалог», форма заявки (ФИО, телефон, компания, согласие) прямо в чате, подтверждение
  3. Режим отладки — переключатель; под ответом бота время ответа и документы базы знаний, раскрываются по клику
  4. Панель менеджера: заявки с резюме и статусами + история всех сессий, включая диалоги без заявки
- **Состояния, продумать до кода:** основной путь (вопрос → уточнение → рекомендация → заявка → её видит менеджер);
  клиент не хочет оставлять контакты; долгий ответ или ошибка; вопрос не по теме; «Новый диалог»; телефон
- **Стиль МТС**, палитра снята из PDF с ТЗ: акцент `#FF0032`, фон `#E0DFF1`, карточки `#FFFFFF`, текст `#282828`,
  второстепенный `#5C5C5C` / `#8C8C8C`, дополнительный акцент `#6451B8`; белые карточки с крупными скруглениями, как в ТЗ.
  Фирменные шрифты МТС закрытые — открытый аналог (Inter или Manrope). Логотипы и картинки МТС не копировать
- **Порядок работы:** сценарии и состояния → кликабельный набросок на моках → утвердить → код → проверка скриншотами
- **Скилы дизайна:** Impeccable — плагин (`/impeccable …`), каждый ставит сам: `/plugin marketplace add pbakaus/impeccable`,
  затем `/plugin install impeccable@impeccable`; его хук после правок интерфейса запускает проверку дизайна
  (программу-проверялку скачивает с GitHub при первом запуске). Скилы Эмиля Ковальски — в `.claude/skills/`
  (анимации и полировка; `prototype` — несколько вариантов интерфейса с переключателем; MIT, лицензия в каждой папке)
- **В презентации как развитие:** тот же бот в Telegram и помощник для региональных менеджеров МТС (пятая группа ЦА)

## Команды (из корня проекта, venv — `.venv` с httpx и numpy)
- Локальный прогон на демо-вопросах: `.venv\Scripts\python eval\run_local.py [--limit 5] [--workers 1]` →
  `runs/<время>/report.md` (наш ответ рядом с эталоном, длина, время, источники). По умолчанию LM Studio на :1234
- Сборка сабмита с проверками по регламенту: `.venv\Scripts\python scripts\make_zip.py` → `dist/submission.zip`
- В Windows у пользователя системный прокси VPN (`127.0.0.1:10809`): `llm_client` ходит к localhost мимо него,
  иначе LM Studio отвечает 503

## Запуск бэкенда (текущий)
Из папки `backend/`: `python -m venv .venv` → `.venv\Scripts\activate` → `pip install -r requirements.txt` →
`uvicorn app.main:app --reload --port 8000` → http://localhost:8000, панель менеджера — `/manager`

## Локальная разработка
- Прокси организаторов доступен только при проверке сабмита. Локально — LM Studio (localhost:1234, OpenAI-совместимый),
  модель Qwen3-VL 8B (RTX 5060, 8 ГБ; 27B не помещается), ~8 с на вопрос. bge-m3 и реранкера локально пока нет.
  8B заметно слабее платформенной 27B: выводы о качестве по локальному прогону — приблизительные
- Сабмиты тратить только на изменения, которые улучшили локальный eval

## Правила
- Работаем командой: интерфейсы между частями (ядро → бэкенд, HTTP API → фронт, БД, переменные), зоны ответственности
  и правила git — в `CONTRACTS.md`. Меняешь интерфейс — правь контракт в том же PR. Сабмиты — в `SUBMISSIONS.md`
- `данные/`, `data/`, `.env` не коммитить. Данные кейса не публиковать и не передавать третьим лицам
- Секреты только в `.env`; ключи не писать в код, файлы и логи
- В тестах — только выдуманные персональные данные
- Не придумывать цены, сроки, тарифы и проценты экономии — ни в ответах бота, ни в README, ни в презентации
- Комментарии в коде и тексты UI — на русском
